# WhereNova — MVP functionality audit

**Date:** 2026-08-29
**Baseline:** local `main` @ `d97ee04` (git fetch to `origin/main` failed in this
environment — no SSH key for `git@github.com`; git reports the local checkout
was already up to date with `origin/main` from a prior fetch, and this matches
the live Base44 preview's own version history, so it's used as-is). See
**Could not verify** at the end for the exact caveat.
**Method:** This is not a code-reading-only audit. Local `npm run dev` cannot
reach `/results` (no backend), so instead:

1. The live 54-destination `Destination` catalogue was pulled from the actual
   Base44 production data store (Dashboard → Data → Destination → Export, in
   the live editor at `app.base44.com`) and converted to JSON.
2. The **actual, unmodified** `src/lib/scoring.js`, `src/lib/practicality.js`
   and their real dependencies (`options.js`, `regionalRoutes.js`,
   `coordinates.js`) were bundled with esbuild and run in Node against that
   real data — `rankDestinations()`, `scoreDestination()`, `buildReasons()`
   etc. executed for real, not simulated.
3. The live app itself (Base44 editor preview iframe, an already-authenticated
   session at `preview--travel-up-go.base44.app`) was driven directly for
   things that only exist at runtime: saved-trip persistence, "Clear my
   data," and refresh behaviour.

Evidence is labeled per item as: **Ran (real data)** — executed the real
scoring/practicality code against the live catalogue; **Live browser** —
clicked through the actual running app; or **Read code** — traced logic
without executing it. Ran/Live is materially stronger than Read and is
called out explicitly where it changes the confidence of a finding.

The questionnaire flow and destination modal were spot-checked only (per
scope) — both loaded and functioned normally with no console errors during
the Area 4 session.

## AREA 2 — Practicality and travel-time correctness

| Item | Status | Evidence | Issue / gap | Beta priority |
|---|---|---|---|---|
| Formula trace | Works | Read code, cross-checked against Ran (real data) output | Documented below; every live-run number matched the formula exactly | — |
| 3-day Vancouver boundary | Works | Ran (real data) | 9 destinations pass, all short-haul (≤6.8h); none implausible | — |
| 14-day Vancouver long-haul eligibility | Works | Ran (real data) | All 54/54 destinations pass; no over-filtering | — |
| Travel-time plausibility (10 samples) | Works with caveats | Ran (real data) against live catalogue | One clear formula gap, one label-accuracy bug (below) | Should fix |
| `min_days` set sensibly + actually protective | **Broken (documentation/behavior mismatch)** | Ran (real data) + Read code (grep across `src/`) | `min_days` has **no role at all** in the eligibility gate | Should fix |

**Q1 — Formula trace** (`practicality.js`, confirmed line-for-line against live execution output):

- **`oneWayHours`** (non-override path) = `flightHours(distanceKm) + overhead + connectionBurden(distanceKm) + connection_hours + internal_access_penalty`, where:
  - `flightHours(km) = km/800 + 0.75` (≈800 km/h cruise + 45 min taxi/climb/descent)
  - `overhead` = 1.5h domestic / 2.5h international (flat, no distance/region tiering)
  - `connectionBurden(km)` = 0 under 4,000km, 2h under 8,000km, 3h under 12,000km, 5h beyond
  - `connection_hours` / `internal_access_penalty` are per-destination authored fields, applied in full regardless of which origin the traveller selected
  - Override path (regional routes: drives/ferries/trains) replaces all of this with a single curated `oneWayHours` value per origin/destination pair.
- **`usableDestinationDays`**: non-override path buckets `oneWayHours` into a tier — `fold` (≤5h, lose 0 days), `partialFold` (≤8h, lose 1 day round-trip), `medium` (≤15h, lose 2 days), `long` (>15h, lose 4 days) — then `tripDays − daysLost`, floored at 0. Override path instead computes continuously: `tripDays − roundTripHours/24`, rounded to the nearest half-day. Both were confirmed to match live output exactly (e.g. Whistler, `oneWay=2h`, `tier=fold`, `usableDays=tripDays` exactly, for every trip length tested).
- **`minUsableDays(tripDays)`**: 1.5 (≤4 days), 2 (≤7 days), 2.5 (≤10 days), 3 (>10 days) — a fixed step function, independent of the destination.
- **`isPractical`**: `usableDestinationDays >= minUsableDays(tripDays)`.

**Q2 — 3-day trip from Vancouver.** 9 of 54 destinations pass: Whistler (2h), Kelowna (4.5h), Victoria (4h), Canadian Rockies (3.1h), Las Vegas (5.2h), San Diego (5.6h), Montréal & Québec City (6.8h), Napa and Sonoma (6.3h), Tofino (6h). All short-haul/regional; **none implausible** — no long-haul destination slipped through.

**Q3 — 14-day trip from Vancouver.** All **54/54** destinations pass, including 39 with a computed one-way time ≥15h (e.g. Cape Town 33.8h, South Island NZ 29.7h). Nothing is over-filtered at this length.

**Q4 — Travel-time plausibility, 10 sampled pairs** (ran the real formula against live data):

| Origin → Destination | Computed one-way | Real-world nonstop (approx.) | Verdict |
|---|---|---|---|
| Vancouver → Tokyo & Kyoto | 18.7h | ~10h flight | Generous but defensible — includes onward Tokyo→Kyoto rail |
| Vancouver → Whistler | 2h (drive) | ~2.5h drive | Plausible |
| New York → Paris | 13.3h | ~7.5h flight | Generous (assumes a connection); **see label bug below** |
| New York → Tanzania & Zanzibar | 28.8h | ~20–24h w/ connections | Plausible for multi-connection long-haul |
| London → Dublin | 2h (override) | ~1–1.5h | Plausible — and confirms a previously-flagged issue (Dublin showing ~4.3h, noted in `docs/qa/travelup-investigation-2026-08-25.md`) is now fixed via a regional-route override |
| London → Bangkok, Chiang Mai & Krabi | 22.2h | ~11.5h flight | Generous (~2x), on the high side |
| Sydney → South Island, NZ | **11.7h** | **~3–3.5h direct flight** | **Implausible — see below** |
| Sydney → Iceland | 34h | ~30h+ w/ connections | Plausible |
| Toronto → Cartagena | 10.9h | ~6–8h w/ 1 connection | Generous but defensible |
| San Francisco → Napa and Sonoma | 1.5h (drive) | ~1–1.5h drive | Plausible |

Two real, confirmed issues surfaced by this sample:

1. **Origin-agnostic connection overhead inflates nearby routes.** South Island NZ carries fixed `connection_hours: 3` + `internal_access_penalty: 3` (6h flat), authored for a traveller connecting through Auckland from a distant origin. Applied uniformly, it makes a Sydney traveller's actual ~3.5h direct flight to Christchurch/Queenstown display as 11.7h — over 3x the real time. This is a **general formula limitation**, not a one-off: any destination's `connection_hours`/`internal_access_penalty` is a single value regardless of how close or direct the selected origin actually is. In the scenarios tested this didn't cause an eligibility-gate failure (short NZ trips from Sydney still pass), but it does understate practicality and depress the score via `travelPenalty` for origins that are actually closer.
2. **`travelMode` display text is not origin-aware.** In the non-override path, `practicality.js:179-183` falls back to `dest.travel_mode` whenever it's present — but this field is a single authored string per destination, sometimes written assuming a specific nearby origin. Paris's `travel_mode` field reads **"Direct Eurostar train"** (written for a UK/European origin), and it is shown verbatim on the "Getting there" fact for **any** origin without a regional-route override — including New York, where the actual computed number (13.3h) uses the flight formula but the label falsely claims a train that doesn't run from New York. Confirmed live: this exact record is what showed on the Paris saved-trip detail page during Area 4 testing. This directly touches the audit's stated top risk (recommending/describing a trip that doesn't physically work) and should be fixed — either compute a generic mode string for non-override routes, or scope `travel_mode` to the override table only.

**Q5 — Is `min_days` set sensibly, and does it actually protect against unrealistically short bookings?** The values themselves look internally consistent (a `grep` across all 54 found no destination with `min_days > max_days` or `min_days < 1`; short-haul/UK-cluster destinations sit at 2 days, long-haul destinations at 6–8 days, in line with their travel-time tier). **But the premise in the brief is not true of the current code.** A full-repo search (`grep -rn "min_days" src/`) shows `min_days` is used only in: (a) `scoring.js`'s soft preference "trip length fit" score (worth up to 15 of 100 points, not a gate), (b) `discoveryCollections.js`'s "quick getaway" filter/display text, and (c) `storage.js`'s saved-trip display. **It plays no role whatsoever in `isPractical()`/`minUsableDays()`**, which is the actual gate preventing unrealistically short bookings — that gate is driven entirely by the travel-time tier system described in Q1, independent of any per-destination authored value. So: if `min_days` were ever set wrong on a drive-heavy destination, no unsafe booking would slip through (the separate tier gate would still catch it) — but conversely, the documented claim that `min_days` is "the real lever" protecting against this is factually incorrect as implemented, and should either be fixed in the code (make `min_days` participate in the gate) or corrected in the documentation.

*Trivial, no functional impact:* `src/lib/coordinates.js` defines the `uruguay` key twice in `COUNTRY_CENTROIDS` (lines 160 and 239, identical values) — esbuild flags it as a duplicate-key warning. Harmless dead code, worth a one-line cleanup.

**Q1/Q2 — Score spread and clustering**, 8 varied profiles run against the full live 54-destination catalogue (min/max/median over all eligible destinations; top-10 spread = highest minus 10th-highest):

| Profile | Eligible | Min–Max (median) | Top-10 spread |
|---|---|---|---|
| P1 Vancouver, Nature/Hiking/Wildlife, Budget, 10d, Relaxed | 54 | 44–86 (64) | 13 |
| P2 NYC, Cities/Food/Photography, Premium, 7d, Fast-paced | 54 | 42–92 (68.5) | 14 |
| P3 London, Beaches/Relaxation, Comfortable, 14d, Oct | 54 | 30–88 (57) | 20 |
| P4 Sydney, Adventure/Hiking, Moderate, 12d | 54 | 42–95 (59.5) | 20 |
| P5 Toronto, History/Food, Comfortable, 9d, March | 54 | 34–100 (71) | 13 |
| P6 SF, Nature/Photography, Premium, 5d | 14 | 64–90 (79.5) | 15 |
| P7 London, Wildlife/Adventure, Budget, 14d, Family | 54 | 19–78 (48) | 15 |
| **P8 Vancouver, no interests, no climate pref, flexible month** | 54 | 40–70 (62.5) | **2** |

For 7 of 8 varied, realistic profiles, differentiation is healthy — top-10 spreads of 13–20 points, real separation between best and 10th-best match. **P8 is the concerning case, and it's a real, empirically-confirmed one**: a user who leaves interests unselected, climate on "No preference," and month "flexible" gets a top 10 clustered within **2 points** (68–70), i.e. the exact "decoration, not information" failure mode the brief describes. This isn't hypothetical — it's what the live scoring code actually produces for a plausible, easy-to-reach input state (skip every optional-feeling field). Separately, P5 shows 4 destinations tied at exactly 100 — a natural ceiling effect (100 is the maximum possible base score), not a bug, but worth knowing the top of the range can plateau for well-matched domestic trips.

**Q3 — "No preference" behaviour, verified empirically.** Ran `rankDestinations()` with `climate: "No preference"` vs. `climate` key entirely omitted — **byte-identical results for all 54 destinations, in both score and rank**. But the *mechanism* the brief asked to verify (`levelDistance`/`BUDGET_ORDER.indexOf` returning -1) is **not what actually happens for climate**. Climate has its own dedicated early-return branch (`scoring.js:100-102`): `if (!prefs.climate || prefs.climate === "No preference") climate = 10` — i.e. it awards **full/maximum credit (10/10) to every destination**, not a skipped/zero contribution. This is applied uniformly, so it is still rank-neutral in effect (a flat +10 to everyone doesn't change relative order) — the practical claim holds — but the underlying mechanism is different from what was documented, and is inconsistent with how an actually-unset field behaves elsewhere: tested `budget: undefined` (the real `indexOf(-1)` path) separately, and confirmed it gives **zero** credit to every destination, not full credit. Both are rank-neutral, but they move the absolute score by opposite amounts (+10 vs. +0), which matters if scores are ever compared across different users/sessions rather than only within one ranking. Recommend correcting the documentation rather than the code — the current behavior (full credit for "No preference") is arguably the more sensible product choice.

**Q4 — Are `buildReasons()` reasons accurate?** Yes, in the sense that every reason string is gated on the real `breakdown` values that moved the score (e.g. "Enjoyable in your chosen month" only appears when `season >= 12`). But they are **generic**: two structurally different destinations with an identical breakdown produce byte-identical reason text. Confirmed live in the P2 (NYC) run — New York City and Istanbul & Cappadocia, both scoring in the top 3 with an identical `{season:20, interest:21.7, budget:15, length:15, climate:10, pace:10}` breakdown, produced the exact same three reason strings: *"Great for cities, food, photography" / "Enjoyable in your chosen month" / "Fits your selected budget level."* `Results.jsx`'s `withDedupedPills()` mitigates this only for the 3 cards shown together on one results page (falls through to `top_experiences` on a repeat) — it doesn't address the underlying genericness if a user revisits with different top-3s across sessions.

**Q5 — Determinism.** Confirmed: 5 repeated runs of the same profile against the same data produced byte-identical ranked output every time.

## AREA 4 — Saved trips and data persistence

| Item | Status | Evidence | Issue / gap | Beta priority |
|---|---|---|---|---|
| Pre-Phase-2 trip (no `score` field) renders correctly | Works | Read code (schema validator + every consumer's `typeof === "number"` guard) | Not tested with an actual legacy fixture — see Could not verify | — |
| Packing state isolated per saved trip | Works | Read code (`SavedTripDetail.jsx`) | Structurally isolated by trip `id`, not shared | — |
| Snapshot vs. live re-read on destination data change | Works | Read code, explicit self-documenting comment | Confirmed never calls the Destination entity API | — |
| "Clear my data" fully clears saved trips + questionnaire answers | Works with caveats | **Live browser**: clicked through the real flow | Storage is correctly and fully cleared, but the UI doesn't refresh in place | Should fix |
| Guest persistence across refresh | Works | **Live browser**: reloaded the live preview | Saved trips + prefs survived a full reload | — |

**Q1 — Pre-Phase-2 saved trip.** No trip predating the `score` field was available to open live in this session (only one pre-existing saved trip existed, "Paris," and it already had the field). Verified instead by tracing the exact guard logic: `isValidSavedTrip()` (`storage.js:173-177`) does **not** require `score`, `buildTripSnapshot()`'s own comment states old saves "simply omit it," and the only consumer that renders it, `SavedTrips.jsx:131`, gates on `typeof t.score === "number"` — which is `false` for both `undefined` (an old trip missing the key) and `null` (the explicit fallback) — falling through cleanly to a qualitative "Travel Fit: [Good fit]" badge instead of a numeric ring. No crash path, no `NaN`/`undefined` rendering found anywhere this field is consumed. This is strong code evidence but not a live-clicked confirmation with a real legacy record.

**Q2 — Packing isolation.** Confirmed by code: `SavedTripDetail.jsx` reads and writes packing exclusively via `trip.packing` / `updateSavedTripPacking(trip.id, ...)` — each saved trip carries its own embedded `packing` object inside its own array entry, keyed by that trip's unique `id`. This is structurally separate from the shared `packingByTrip[fingerprint]` store used only for the in-progress (not-yet-saved) trip flow. Two saved trips cannot share packing state by construction.

**Q3 — Does a saved trip re-read live data or hold a snapshot?** Snapshot, confirmed unambiguously. `buildTripSnapshot()` copies every destination field (name, country, image, intro, top experiences, etc.) verbatim into the saved record at save time, and `SavedTripDetail.jsx` carries this comment directly above the component: *"Renders a saved trip purely from its immutable snapshot. It never calls the Destination entity API, regenerates itinerary/packing/overview, or changes current preferences / selectedDestinationId."* So if a destination's images or content regenerate later (as literally just happened for Victoria, Tofino, and Tanzania & Zanzibar per the live Base44 build log seen during this session), an existing saved trip for one of those destinations would **not** pick up the new images — it would keep showing whatever was live at save time. This wasn't re-verified with an actual before/after saved trip for one of those three (see Could not verify).

**Q4 — Does "Clear my data" fully clear everything?** Tested live end-to-end. Before: Home showed a "Your Travel Fit: 10-day trip from Dublin · October · cities and relaxation" banner and a "Continue your saved trips" rail with one Paris trip. Clicked "Clear my data" → a real (non-native) confirmation dialog appeared, correctly scoped: *"This permanently deletes from this browser: your questionnaire answers, current destination selection, current and active-trip packing progress, and every saved trip with its packing progress. This cannot be undone."* Confirmed. **Bug found live:** immediately after confirming, the current page did **not** re-render — the Travel Fit banner and the Paris saved-trip card remained visible on screen exactly as before. Reloading the page confirmed the underlying data genuinely was cleared (banner gone, "Saved trips" page shows "No saved trips yet") — so the deletion itself is correct and complete, but the missing in-place refresh means a user has no immediate visual confirmation that an explicitly-irreversible action worked, which could plausibly cause them to click "Delete all local data" again or distrust the result. No orphaned state was found beyond this: all product state lives under one `localStorage` key (`travelup_state_v1`), removed atomically; the only other `localStorage` usage in the codebase (`app-params.js`) is unrelated Base44 SDK plumbing (app id, access token) that "Clear my data" correctly leaves untouched.

**Q5 — Guest persistence across refresh.** Confirmed live: reloaded the app before clearing data, and both the saved Paris trip and the "Your Travel Fit" preference banner persisted exactly as before (as expected for `localStorage`-backed state, not session-only).

*Incidental content finding, surfaced while reading the Paris saved-trip Overview tab live:* Paris's live `top_experiences` field contains the literal string **"Louvre or Musée d'Orsay (deterministic choice)"** — confirmed present in the current live Destination record (not just the saved snapshot), i.e. this is what every user currently sees. Reads like a leftover debugging/test annotation from prior itinerary-selection-logic work, not intended user-facing copy. Content fix, not a code bug.

## Highest-priority items to address next

1. **Fix the `travelMode` label bug (Area 2, Q4).** The "Getting there" fact shown on every result/trip card can display a transport mode that has nothing to do with the traveller's actual origin (e.g. "Direct Eurostar train" shown to a New York traveller). This is a factual-accuracy problem on the exact claim the audit brief flags as highest-risk (recommending a trip that doesn't physically work).
2. **Fix "Clear my data" not refreshing the current page (Area 4, Q4).** The deletion itself works and is complete, but the missing re-render undermines user trust in an explicitly irreversible action.
3. **Correct the `min_days` documentation (Area 2, Q5).** It is not, as implemented, a lever against unrealistically short bookings on drive-heavy destinations — the tier-based practicality gate is the only real protection, entirely independent of `min_days`. Either wire `min_days` into the gate or fix the documentation so no one relies on a protection that doesn't exist.
4. **Address score clustering for under-specified profiles (Area 3, Q1/Q2).** A user who skips interests/climate/month gets a top-10 spread of 2 points — confirmed with real data, not a hypothetical. Worth deciding whether to nudge users toward selecting at least one interest, or accept this as an edge case.
5. **Fix the `Results.jsx` header grammar/layout for 0/1/2-result pages (Area 1, Q5).** "Your top 0 matches" / "Your top 1 matches" and a lone card in a 2-column grid are small but real, easily-reachable rough edges (reachable via ordinary domestic-only or single-country-catalogue scenarios, not just adversarial inputs).

## Product decisions required (cannot be made by this audit)

- **The fewer-than-3 / zero-result question itself (Area 1).** The gate is absolute by design and there's no code path that relaxes it. Is showing 1–2 results (or 0, with a "try again" prompt) the intended MVP behavior, or should the catalogue/gate be revisited so this happens less often? This is squarely the product decision the brief anticipated.
- **Whether `min_days` should actually gate bookings**, or stay a pure scoring-only signal as it is today (Area 2, Q5).
- **Whether "No preference" should award full credit (current behavior) vs. truly remove the dimension from scoring** (Area 3, Q3) — both are defensible, but the documentation should match whichever is intended.
